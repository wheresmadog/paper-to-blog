When the Repository Is Documentation, Not Code

A team at Google DeepMind, MIT, Stanford, and Google built a machine-learning performance model whose main branch contains almost no source. Humans edit prose; agents rebuild the library from scratch every version.

On Design Docs Are All You Need: An AI-native Machine-Learning Performance Tool, by Samuel Kushnir, Kimia Noorbakhsh, Kavya Sreedhar, Liqun Cheng, Ming Liu, Parthasarathy Ranganathan, Mohammad Alizadeh, Fred Kjolstad, and Suvinay Subramanian. arXiv preprint, September 2026.

The question

Here is the question the paper puts on the table: if regenerating a whole library from its specification now costs a few hours and about a hundred dollars, why patch the old one again? The authors' answer is that you would not, and they have rearranged a real internal tool around it. Their system, SMART, is a symbolic performance-modeling library for ML systems whose main branch holds roughly 50 design documents — about 9,000 lines of specification prose — plus a handful of leaf utilities.

Everything else is a build product. Coding sub-agents read the docs and emit the implementation; every human change is a natural-language edit to a doc. The paper frames this as a claim about which artifact deserves to be durable: prose, the authors argue, survives architecture churn better than code that encodes today's assumptions about it.

This is a five-page position piece rather than a full evaluation, and reading it that way matters for judging what it establishes. What follows is the argument, the machinery behind it, and the gap between the two.

Why performance models rot faster than most software

Performance-modeling frameworks sit between the two fastest-moving layers of the stack — model architectures above, accelerators and interconnects below — and absorb churn from both directions. An abstraction that looked safe a year ago, say that every transformer layer has the same shape, collapses once mixture-of-experts routing, latent attention, and separate prefill and decode phases arrive.

The paper formalizes the cost of incremental maintenance. Let St be the spec at time t and G a code generator, human or agent. A greenfield build computes G(St); in practice the next revision hands the generator the old implementation too, computing G(St+1, Ct). Technical debt is the distance between the two. Because deleting your own code is unpleasant and slow, that distance stays well above zero and compounds with every revision.

A second failure mode is specific to the AI era, which they call context-window myopia: an agent cannot hold a mature codebase in one prompt, so developers feed it fragmented snippets. Missing global invariants and architectural intent, it produces changes that are locally plausible and globally incoherent. Regenerating from scratch drives the first term to zero by construction; the document structure addresses the second.

The regeneration workflow

The docs form a directed acyclic graph — hardware topology and numerics precede collective-cost models, which precede the model catalog. The edges are not hand-maintained: read-only agents analyze the documents and infer the dependencies themselves. An orchestrator then walks the resolved graph in topological order, assigning one coding sub-agent per self-contained doc.

The orchestrator keeps a central log of where sub-agents struggled to interpret prose and what bugs surfaced in earlier waves. The paper draws three benefits from this factoring: each generation step has a bounded context window, which the authors say raises the probability of correct generation; the log tells engineers which documents need prose refinement, a per-doc "hardness" signal; and the orchestrator can route by complexity, sending the core DSL design to a larger model while cheaper models handle downstream docs.

Output must clear a gate before replacing the previous build: reconciliation against hand-built reference models, parameter guards, and unit tests, with a repair loop on failure. The stated economics: a full clean-slate regeneration takes 1.5 to 3 hours and costs around 100 USD in API spend using Claude Code — roughly 20% of a weekly budget on a high-tier plan, which the authors read as making continuous regeneration practical.

Worked examples as the load-bearing convention

The most transferable idea concerns how the docs are written. Prevailing advice for AI-assisted development is top-down: write the right tests and high-level rules, a constitution the generator must obey. The authors argue for a complementary bottom-up ingredient — worked examples tracing how a piece of pseudo-code executes on a specific input, with intermediate shapes, intermediate values, and the exact closed-form cost expression that should result.

Their reasoning is that a concrete trace pins down semantics prose leaves ambiguous, keeping independent agentic generations consistent with each other; they cite in-context learning as the mechanism. The style is deliberately small and checkable: on a 2×2×2 torus with wraparound the per-node link count is 3, not 6, so an all-gather of V bytes costs such-and-such. Every number-bearing doc ends with a reconciliation anchor — a small preset whose expected outputs are stated exactly and enforced by generated tests.

This is worth separating from the larger thesis. You need not accept that repositories should become documentation to take the narrower point: a spec with hand-executed traces gives a generator something to check itself against and a reader something to disagree with. The paper presents it as a principle they arrived at, not a hypothesis tested against an alternative doc style.

A minimal symbolic IR

Regeneration also constrains what is specified: the abstractions must be few, orthogonal, and stable under architecture churn. The whole model rests on a single recursively defined operation. An Op carries symbolic input and output shapes, an OpCost of SymPy expressions per cost key (compute, memory, communication), and a resource reservation table mapping resources against cycles. It is either an interior node — a loop with a trip count and body graph, or a plain subgraph — or a leaf.

Leaves are where software meets hardware. The target is TPUs, so leaves are TPU-shaped: an MXU matmul tile, a VMEM tile load, an ICI collective. The algorithm side composes leaves into loop nests; the system side prices them. Swapping either — a new attention variant, a new interconnect generation — touches only its own docs. Models are authored in a thin Python-embedded tracing DSL where every dimension is a SymPy symbol, so one trace serves the whole design space.

Distribution is expressed as sharding annotations rather than hand-placed collectives: tensors name the mesh axes each dimension is sharded on, and a sharded-einsum wrapper infers the collectives — an all-gather of a sharded contracting weight, a reduce-scatter when an output reduces over a sharded dimension. Only layout-moving collectives stay explicit, such as the dispatch all-to-all in a DeepSeekMoE block.

Two speeds of evaluation

Turning a tree of per-op costs into wall-clock time happens in one of two modes. In fast mode, loops roll up coarsely: each leaf's cost is scaled by the product of enclosing trip counts, and simple analytical schedulers model communication–computation overlap as composable transforms in the style of a roofline bound. Evaluation is closed-form and fast enough to sweep thousands of design points.

In slow mode, each loop is modulo-scheduled into its resource reservation table, software-pipelining the body against per-resource capacity, and the achieved initiation interval rolls up recursively. That yields dependency- and resource-aware schedules for the points sweeps flag as interesting — the familiar division of labor between cheap approximation and expensive analysis.

Underneath both, costs propagate upward symbolically, so every roll-up produces a closed-form SymPy expression in the design space's free variables — batch, sequence length, bandwidths, mesh axes, datatype widths. Numeric binding happens only at the edge, one substitution per design point. This is also what makes the reconciliation anchors enforceable: a doc can state the exact expected expression for a collective's cost, and the generated tests assert it.

What this paper does not show

The central empirical claim appears in the abstract and conclusion: regenerated implementations reproduce hand-audited reference models — including DeepSeek-V3 serving on a TPU pod slice — to round-off precision. The body contains no experiments section, no results table, and no description of how that reconciliation was measured. Treat it as a reported engineering outcome from the authors' practice, not a demonstrated result with an inspectable methodology.

Much else goes unmeasured. There is no comparison against an incrementally maintained baseline, so the debt term in Equation 1 is argued rather than quantified. There is no reported regeneration failure rate, no measure of how often the repair loop fires, and no ablation separating worked examples from the DAG structure or the minimal IR. The cost and time figures are stated for this library at its current size and are not projected to larger systems.

Scope matters too. Reconciliation validates a build only insofar as the hand-built references are correct, and the paper does not say how they are maintained as the docs evolve. The domain is also unusually favorable: a performance model is a pure function with checkable numeric outputs, targeted at one hardware family. Nothing here establishes that the workflow holds for software with state, external dependencies, or no closed-form oracle.

Why it is interesting anyway

The idea worth carrying away is the inversion of what a repository is for. Conventionally, code is the artifact and documentation the lossy commentary that drifts out of date. Here documentation is the artifact and code the build output — self-documenting by construction, and, as the authors put it, surfacing vague intent early, because a guess must be written into a doc to survive.

The authors are careful about where they think this generalizes: wherever specs churn faster than software absorbs them. That is a real and narrow condition, and ML performance modeling satisfies it about as sharply as any domain. The three enablers — worked-example docs, a machine-discovered dependency DAG, and a minimal symbolic IR — are separable, and the first is adoptable today by anyone writing specs for an agent, independent of the rest.

The unresolved question is what happens to the reference models. Regeneration drives patching debt to zero only because a trusted oracle catches regressions, and that oracle is still hand-built and hand-audited. If the references are themselves code that ages, the debt has not been eliminated so much as relocated to a smaller, more critical surface — which this position piece leaves to future work.
